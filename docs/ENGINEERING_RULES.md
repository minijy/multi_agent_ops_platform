# SellerForge 工程规则

> 本文档来自项目多轮改造的问题复盘。目的不是记录某次修复，而是将容易反复出错的设计边界变成后续开发必须遵守的规则。

前端页面、状态机、文案、角色可见性和视觉验收的详细规则见 [FRONTEND_RULES.md](FRONTEND_RULES.md)。

## 1. 完成的定义

1. 不得将“已写代码”等同于“功能完成”。
2. 对外宣称完成前，至少需要满足：
   - 主流程可实际运行。
   - 错误分支有用户可理解的反馈。
   - 聚焦测试和项目全量回归通过。
   - 前端调用的每个 API 在后端都有实际路由。
3. 涉及 PostgreSQL、Qdrant、Milvus、真实模型或外部 OpenAPI 时，未连接真实基础设施验证只能标记为“代码和模拟测试通过”，不得标记为“生产可用”。
4. 交付时必须分开写明：已实现、已验证、未验证、后续优化。

## 2. RBAC 和 Tool 权限模型

1. 用户与权限组是多对多关系。
2. 权限组与业务 Tool 是多对多关系：
   - 一个权限组可授权多个业务 Tool。
   - 同一个 Tool 可出现在多个权限组。
   - 同一权限组内不得重复授权同一 Tool。
3. Tool 权限的编辑入口必须在“权限组”上，使用可多选的下拉框或检查列表。
4. “规则明细”是结果视图，只读展示；不得在明细卡片上提供移动、改组或重复授权操作。
5. `remember_fact`、`search_memory`、`forget_memory`、`load_skill`、沙箱基础能力、`delegate_subagent` 和 `delegate_specialists` 属于 Agent 运行基础 Tool：
   - 默认对所有可运行 Agent 的用户可见。
   - 不出现在业务权限组候选项中。
   - 仍需受 Agent 职责、记忆同意和沙箱安全策略约束。
6. `admin` 默认拥有全部业务 Tool 权限，但不得绕过：
   - Agent 职责白名单。
   - Connection 数据范围。
   - 高风险操作审批。
7. 最终 Tool 可执行范围必须统一计算：

   `身份权限 ∩ Agent Tool 白名单 ∩ 权限组业务 Tool 授权 ∩ Connection 数据范围`

8. 权限拒绝必须返回结构化错误，至少包含 `code`、被拒绝的 Tool、原因和管理员处理建议。不得让模型伪装成“已委派，请等待”。

## 3. Connection 和数据边界

1. Connection 是独立配置对象，Tool 通过页面选择 Connection，不得将连接凭证再写回 Tool 配置。
2. 已经有页面配置的项，运行时以控制面数据为真实源；配置文件只允许作为明确标注的启动引导或兼容回退。
3. 凭证与公开配置分离存储，API 和页面只返回“已配置”状态，不得回显密钥。
4. 保存 Connection 时必须验证 URL/DSN 格式，并将 FastAPI 422 中的字段错误翻译为页面可理解的提示。
5. “有 Tool 权限”不等于“可访问所有数据”。Tool 绑定的数据范围和 Connection 允许的数据范围必须取交集。
6. 表名、内部字段名、DSN、Collection 内部标识等实现细节默认不向普通用户暴露。结果只展示可读的“数据来源”名称。
7. 存在多个同类数据 Tool 时，Agent 必须优先选择当前用户有权限且 Connection 可用的 Tool，不得先推荐一个不可用的来源再让用户确认回退。

## 4. 模型配置规则

1. 初始化后不得内置 Mock 模型或隐式使用环境密钥。未在页面完成可用模型配置时，对话必须明确阻止。
2. API Key 为空时不得使用历史值、前端密码管理器显示值或其他 Provider 密钥继续调用。
3. 模型必须显式配置能力：文本、图片、语音、Tool Calling、结构化输出和 Thinking。
4. 只有当前模型声明支持相应能力时，前端才展示图片/语音入口，Runtime 才允许发送该类输入。
5. 结构化抽取、Embedding 和主对话可使用不同模型，不得默认把高成本主模型用于所有后台任务。

## 5. Multi-Agent 委派和队列

1. “多 Agent”指可差异化的专业 Agent 实例，不是同一 Analyst 名称的多次串行调用。
2. 必须保留两种显式模式：
   - 通用 Analyst。
   - 并行专业 Analyst，最多同时运行 3 个。
3. “并行”必须由调度器和任务状态证明，而不是仅在提示词中要求模型并行。
4. 每个子任务必须有稳定 `task_id`，状态应按同一条记录演进：

   `queued -> running -> completed | failed | cancelled`

   前端不得把 `queued` 和 `running` 渲染为两个重复任务。
5. Coordinator 只有在子任务都进入终态并收到可用结果后才可结束主任务。“已委派，请稍等”不是最终答案。
6. 委派 Tool 的参数在执行前必须完成 Schema 验证和兼容归一，特别是 `objective` 必须为字符串。模型首次输出错误参数时可进行一次有边界的修复，不得无限重试。
7. 用户无权使用某专业 Agent 依赖的业务 Tool 时，该专业 Agent 不得出现在列表或委派候选中。
8. 中断必须取消尚未执行的队列任务并向正在运行的任务发出取消信号；恢复必须从持久化检查点继续，不得重复执行已完成的写操作。

## 6. 会话、任务和身份隔离

1. 会话、事件、后台任务、子任务、附件和快照的所有读写必须同时校验 `tenant_id + user_id + session_id`。
2. 不得只在权限查询中隔离用户，却在会话列表、事件回放或后台任务中只按 tenant 过滤。
3. 新增 owner 字段后必须处理历史数据归属。不得因为旧记录 `user_id` 为空就让用户的原会话“消失”。
4. 列表、读取、删除、中断和恢复必须使用同一套 owner 判定逻辑，不允许每个 API 自己拼接过滤条件。

## 7. 账户与管理界面

1. 完整账户链路必须包括：注册或管理员建账、临时密码、首次登录强制改密、登录、Token 刷新、退出、停用、锁定和审计。
2. 非 admin 用户不展示运行概览、审批中心、连接器、用户权限、审计日志和系统设置。
3. 长期记忆是用户隐私控制界面，普通用户可访问，但只能看到和管理自己的记忆；租户策略和组织记忆仅 admin 可管理。
4. 菜单隐藏不是权限控制。后端 API 必须独立验证身份与角色。

## 8. 长期记忆规则

1. 长期记忆不由“对话了多久”自动变成，而由明确的写入和治理流程产生。
2. 用户明确说“记住”时才可直接写入显式记忆。自动抽取的内容必须先进入 `candidate`，不得默认污染用户画像。
3. 与已生效事实冲突的候选必须进入 `conflicted`，由用户或管理员确认、替换或拒绝。
4. 每次请求必须支持三种记忆模式：正常读写、只读、临时会话。临时会话不读取、不写入长期记忆。
5. 记忆检索必须先在数据库完成 tenant、owner、scope、status 和过期时间过滤，再进行语义排序。不得先全库向量检索再在应用层隐藏越权结果。
6. 注入提示词的记忆必须标记为“不可信上下文”，其中的指令不得执行。
7. Coordinator 读取小型相关快照；Analyst 使用委派时固化的快照，不直接继承 Coordinator 的全部会话和记忆。
8. 删除必须同时擦除主数据原文、Embedding、向量库 Point、来源摘要和关系数据，只保留不含原文的审计事件。
9. 敏感数据默认禁止保存；审核模式下也只能进入候选状态。
10. 未使用真实 PostgreSQL、Qdrant/Milvus、Embedding 模型、结构化抽取模型和业务评测数据验证前，不得宣称记忆体系已达到成熟产品水平。

## 9. 知识库边界

1. 向量数据库 Connection、知识空间和知识入库管道是三个不同层次，不得混为一个表单。
2. Connection 负责 URL/URI 和凭证；知识空间负责 Collection、Embedding、字段映射、Top K 和过滤字段；入库管道负责文件解析、切片、向量化、版本和任务状态。
3. 知识库页面至少展示知识空间、分类、文档/片段内容、元数据、来源和更新时间。仅显示 Point 数量不能称为知识库管理。
4. 初始化后不得展示 Mock 知识数据或 Mock 检索后端。未配置时应展示引导状态。

## 10. 大数据量和 Token 使用

1. 数据库查询、过滤、分组、排序、汇总、统计和精度计算由 Tool/数据库完成，不得把全量明细传给模型计算。
2. Tool 默认返回 Schema、口径、汇总结果、少量样例和可继续查询的句柄，而不是大表全量文本。
3. 跨月、跨数据源任务应先产生结构化子任务，子 Agent 只返回紧凑的结果对象，Coordinator 负责最终整合。
4. 过程事件、Tool 调用参数和大量原始结果供调试面板按需展开，不得重复注入后续模型轮次。
5. 减少 Token 不得破坏主流程：先做查询下推、结果句柄、去重、快照限额和小模型抽取，再考虑压缩必要上下文。
6. Token 预算是保护线，不是正常终止逻辑。接近预算时应先缩减工具结果、对话历史和子任务回传内容。

## 11. API 和数据库兼容规则

1. 前端新增 API 调用时，同一改动必须增加后端路由和 API 测试，不得留下持续 404 的页面轮询。
2. SQLite 和 PostgreSQL 实现不得假设连接对象 API 相同。例如 psycopg 3 的 `Connection` 不应直接调用 `executemany`，应使用 Cursor 或显式批处理。
3. 每个存储实现必须通过同一套契约测试，包括事务提交、回滚、空值、JSON、时区、批量写入和唯一约束。
4. 迁移脚本、Runtime 自建表和 ORM/SQL 字段必须同源审查，不得出现迁移有字段但 Runtime 不写，或 Runtime 写字段但迁移未创建的情况。

## 12. 前端文案和状态

1. 普通用户文案只说“正在做什么”和“需要用户做什么”，不展示“紧凑结果”、“计算口径”、内部表名或 Tool Schema 等开发语言。
2. 同一 `task_id` 的队列、执行和完成事件必须更新同一个界面节点，不得每个事件追加一张卡片。
3. Tool 调用成功不等于主任务成功。页面的“完成”提示必须基于最终答案已持久化，而不是某个委派 Tool 返回。
4. 返回 401/403/404/409/422/500 时都必须展示具体错误信息，不得统一只显示“出错了”。
5. 页面新增、编辑等低频操作应使用按钮打开抽屉/对话框，不得常驻展示大块空表单。

## 13. 改动和验收流程

1. 改动前先确认当前工作树状态，保留用户已有未提交修改，不得重置或覆盖无关变更。
2. 数据模型改动必须同时检查：迁移、存储层、API Schema、Runtime、前端、文档和测试。
3. 最小验收命令：

   ```bash
   python -m py_compile <changed-python-files>
   git diff --check
   pytest -q <focused-tests>
   pytest -q
   ```

4. 前端 JavaScript 改动应运行 `node --check frontend/app.js`；环境缺少 Node 时必须在交付说明中标记未执行，并用浏览器主流程验证补足。
5. 涉及真实基础设施的改动必须维护验证矩阵：

   | 项目 | 本地/模拟 | 真实环境 | 业务数据 | 结论 |
   | --- | --- | --- | --- | --- |
   | PostgreSQL |  |  |  |  |
   | Qdrant/Milvus |  |  |  |  |
   | Embedding |  |  |  |  |
   | 结构化抽取模型 |  |  |  |  |
   | 外部业务 Connector |  |  |  |  |

6. 发现问题时必须先确定根因属于数据模型、权限、调度、API、前端状态还是外部依赖，不得只根据截图在展示层打补丁。

## 14. 下一阶段真实验证准入条件

在进一步优化记忆流程或 Token 成本前，先完成以下验证：

1. 真实 PostgreSQL：迁移、并发事务、JSONB/pgvector、合规删除和 outbox 重试。
2. 真实 Qdrant：Collection 创建、维度校验、tenant 过滤、upsert/delete、断线重试和重建索引。
3. 真实 Embedding 模型：中英文同义召回、维度一致、批处理、超时和模型版本切换。
4. 真实结构化抽取模型：Schema 稳定性、候选质量、敏感数据、冲突事实、失败回退和 Token 成本。
5. 企业业务评测集：事实、偏好、画像、组织知识、任务经验、时效冲突、跨用户和跨 tenant 隔离。
6. 核心指标：Recall@K、误召回率、候选接受率、冲突检测率、敏感泄漏数、删除后残留数、每轮注入 Token 和主任务成功率。
7. 优化顺序：先修正准确性、权限和可恢复性，再减少候选数、检索数和注入 Token；任何成本优化都不得降低主任务成功率或放松权限边界。
